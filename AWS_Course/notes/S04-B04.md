# S04-B04: IAM Roles and IAM Security Tools

Udemy (Stéphane Maarek), Section 4. Exam link: Task 1.1 (role-based access, least privilege, access visibility). Reviewed 2026-11-04.

## 1. The big idea

AWS services need permissions to act in my account, and I do not want to give them stored keys. Roles do that. Two reports then help keep every identity's access minimal and healthy.

## 2. IAM roles

- **Role:** like a user, but meant for AWS services, not for people.
- **How it works:** a service such as an EC2 instance gets a role, and the two act as one entity. When the instance calls AWS, it uses the role, and the call works if the role's permissions allow it.
- **Common examples:** EC2 instance roles, Lambda function roles, and CloudFormation.
- **No stored keys:** a role gives a service access without an access key sitting on it. Supplemental: the credentials are temporary and are delivered automatically.

## 3. Creating a role

- **Where:** IAM, then Roles, then Create role.
- **Role type:** the console offers five kinds. For this lesson and the exam, choose AWS service. Supplemental: the five are AWS service, AWS account, web identity, SAML 2.0 federation, and custom trust policy.
- **Service and use case:** pick the service, for example EC2, and its use case.
- **Permissions:** attach a policy. The demo used IAMReadOnlyAccess. Supplemental: a role can hold several policies, with a default quota of 20 managed policies and a maximum of 25.
- **Name and review:** give the role a clear name and check the summary before creating it.
- **Trusted entity:** who may assume the role, here the EC2 service. It is mandatory, and its options change with the role type.
- **Trust vs. permissions:** the trusted entity says who may use the role. The policy says what the role may do. Supplemental: the trust is stored as a trust policy, which is where the Principal element appears.
- Supplemental: a role can trust more than one service, but best practice is one role per purpose.

## 4. IAM security tools

- **Credentials Report (account level):** a CSV of all users and the state of their credentials. It shows when each user was created, whether a password is enabled, when it was last used and changed, the next rotation, whether MFA is active, and whether access keys exist, with their last rotated and last used dates.
- **Use:** spot users who deserve attention, such as no MFA, stale passwords or keys, or accounts that are not used.
- **Access Advisor (user level):** shows, for one user, the services they are permitted to use and when each was last accessed. Drilling down shows which policy granted the access.
- **Use:** find unused permissions and trim them. This is least privilege driven by evidence.
- **Not an activity log:** Access Advisor is not CloudWatch (metrics and alarms) or CloudTrail (the record of API calls). Supplemental.

## 5. Decision rules (requirements lead to choices)

- An app on EC2 needs AWS access and no stored key: create a role with only the permissions it needs and attach it to the instance.
- A role will not work for a service: check the trusted entity first.
- I need every user's MFA and credential status in one file: the Credentials Report.
- I want to shrink one user's permissions: Access Advisor, then replace the broad policy with narrower ones and test.
- Never attach AdministratorAccess to a role just to avoid being blocked.

## 6. What I verified in my own account

- I generated the credentials report. It showed which identity had no MFA and which had an active access key. Both of my predictions were wrong, which is the point: use the data.
- I created a role for EC2 with a read-only policy, confirmed its trusted entity, and deleted it afterward.
- The role's last-used information showed an old role from an earlier project that had not been used for weeks.

## 7. Mistakes to watch for (from my own misses)

- Assuming MFA and access keys were set up instead of checking the report.
- Thinking Access Advisor is an activity log like CloudWatch. It shows last-accessed services.
- Mixing up who may use a role (trusted entity) with what it may do (policy).
- Reversing the two tools: the report is account level, and Access Advisor is user level.
- Leaving test roles and users behind. Delete them when the exercise ends.
- Leaving a CLI-only user with a console password and no MFA.
