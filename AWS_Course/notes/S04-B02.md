# S04-B02: IAM Policies and MFA

Udemy (Stéphane Maarek), Section 4. Exam link: Task 1.1 (policy-based authorization, least privilege, MFA). Reviewed 2026-10-26.

## 1. The big idea

Users and groups are not enough. A policy says exactly what an identity may do, and MFA protects the login itself. Policies limit the damage a login can do. MFA makes the login hard to steal.

## 2. Policies: what an identity may do

- **Group policy:** a policy attached to a group applies to every member.
- **Several groups:** a user in more than one group gets the policies from all of them.
- **Attached directly:** a managed policy attached to one user. It is a standalone, reusable object, such as IAMReadOnlyAccess, or one I create.
- **Inline policy:** a policy embedded inside one identity. It cannot be reused and is deleted with that user. Use it only for a true one-off.
- **Where a permission came from:** the console shows it on the user's permissions page, for example "via group admin" or "attached directly."
- **Leaving a group:** removing a user from a group takes the group's permissions away immediately, and the next request is denied.
- **Read-only vs. full access:** with only read-only access a user can view things but cannot create them. That is least privilege at work.

## 3. Policy structure (JSON)

- **Version:** the policy language version, usually 2012-10-17.
- **Id:** an optional name for the policy.
- **Statement:** one or more statements, each with the parts below.
- **Sid:** an optional name for the statement.
- **Effect:** Allow or Deny.
- **Principal:** who the policy applies to (an account, user, or role).
- **Action:** the API calls that are allowed or denied.
- **Resource:** what those actions apply to.
- **Condition:** an optional "only when" rule.
- **Know for the exam:** Effect, Principal, Action, Resource.
- **Wildcards:** * means anything. Action * with Resource * is exactly AdministratorAccess. Get* and List* cover every action that starts with Get or List, which is how read-only policies are written.
- **Building a custom policy:** use the visual editor or write the JSON.
- Supplemental: policies on users and groups do not need a Principal. A resource policy, such as an S3 bucket policy, does.
- Supplemental: an explicit Deny always overrides an Allow.

## 4. Protecting the login

- **Password policy** (IAM, Account settings): minimum length, required character types, letting users change their own password, expiration (for example every 90 days), and preventing reuse. It protects against guessing and brute force.
- **A password policy cannot require MFA.** MFA is a separate control, turned on for each identity.
- **MFA:** something I know (the password) plus something I own (a device). A stolen password alone is not enough.
- **Virtual MFA device:** an app such as Google Authenticator or Authy. Authy can hold many tokens on one device.
- **U2F security key:** a physical key, such as a YubiKey, from a third party. One key can serve several root and IAM users.
- **Hardware key fob:** a small physical device from a third party, for example Gemalto.
- **GovCloud key fob:** a special fob for AWS GovCloud (US) only.
- **Setting up MFA on root:** click the account name, open Security credentials, assign a device, scan the QR code, and enter two consecutive codes.
- **Up to eight MFA devices** can be registered per user. Add a second kind as a backup so a lost phone is not a lockout.
- **Warning from the instructor:** students have locked themselves out by losing their only device. Add a device, test it, and only then rely on it.
- Supplemental: MFA belongs to each identity. Root's MFA does not protect an IAM user.

## 5. Decision rules (requirements lead to choices)

- The same policy is needed for many users, changeable in one place: create one managed policy and attach it to groups.
- One user needs a true one-off exception: an inline policy.
- A password leaks: have the user set a new one, and require MFA so a password alone is never enough. A stricter password policy does not change a password that is already set.
- A physical MFA option that serves several users: a U2F security key.
- Test groups, users, and policies: delete them when the exercise ends, so no forgotten access is left behind.

## 6. What I verified in my own account

- My admin user gets AdministratorAccess only through the admin group, with nothing attached directly.
- No leftover test groups or customer-made policies remain after the exercise.
- Root MFA is on, and my admin user has an MFA device.

## 7. Mistakes to watch for (from my own misses)

- Thinking a password policy can require MFA. It cannot.
- Answering the question I expected instead of the one asked. In the physical-device question I picked the virtual app. Underline the deciding word before choosing.
- Mixing up a policy attached directly with an inline policy. The first is a reusable managed policy, and the second is embedded in one identity.
- Expecting a stricter password policy to change a password that is already set. It applies when passwords are created or changed.
- Calling the key fob a "VPN key," and U2F "UTFA."
