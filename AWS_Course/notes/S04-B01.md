# S04-B01: IAM Users, Groups, and Policies

Udemy (Stéphane Maarek), Section 4. Exam link: Task 1.1 (IAM users, groups, roles and policies). Reviewed 2026-10-22.

## 1. The big idea

Everyone who works in an AWS account needs access, but not everyone should have everything. IAM gives each person their own identity and only the access they need.

## 2. Key terms

- **IAM (Identity and Access Management):** a global service. There is no Region to pick, and the console's Region selector is inactive.
- **Root user:** created automatically with the account. Use it only to set the account up, then stop using it, and never share it.
- **User:** one user represents one person.
- **Group:** a collection of users who work together. A group can contain only users, never other groups. A user can belong to more than one group. A user in no group is allowed but is not best practice.
- **Policy:** a JSON document that describes what a user or group may do. It is plain-language rules, not programming.
- **Inheritance:** a user gets a group's policies through membership. The console shows "Attached via: Group" for these.
- **Least privilege:** give only the permissions needed, no more.

## 3. Using the console

- Create a user under IAM, Users. The course picks "IAM user" because that is the answer the exam expects. Supplemental: for real accounts, AWS recommends Identity Center for people.
- For someone else, leave the password auto-generated and require a change at next sign-in.
- Create a group (the demo uses one named admin with the AdministratorAccess policy), then add the user to it.
- Tags are optional metadata that you can put on any resource.
- An account alias replaces the 12-digit account ID in the sign-in URL with a friendly, unique name.
- Who am I? Root shows only the account ID in the header. An IAM user shows the account ID and the user name.
- Multi-session support keeps you signed in to several identities or accounts in one browser. It replaces the private-window trick.
- Different accounts have separate resources. A volume created in one account is not visible in another.

## 4. Why groups

- Manage permissions once and they apply to every member.
- Permissions stay consistent, and audits are easier.
- Onboarding means adding a person to a group. Offboarding means removing them.
- Changing a group's policy changes access for every member. To change just one person, change their membership.
- If one user is compromised, the attacker gets only what that user could do. Disable that user and the others are unaffected. Least privilege keeps the damage small.

## 5. Decision rules (requirements lead to choices)

- A new person needs the same access as a team: create a user and add it to the team's group.
- A contractor needs short-term access: create a dedicated user with only the permissions needed, and remove it when the work ends.
- The console header shows only an account ID: you are signed in as root.
- Two accounts must stay open at once: use multi-session support.
- Never share a login. Never use root for daily work.

## 6. What I verified in my own account

- My admin user's AdministratorAccess shows "Attached via: Group admin" in the console, and nothing is attached to the user directly. The CLI showed the same.
- The admin group holds the AdministratorAccess policy.

## 7. Mistakes to watch for (from my own misses)

- Thinking user and group access is temporary. It is long-term. Temporary credentials come from roles (later in this section).
- Thinking I can edit a group because root created it. It is my IAM permissions that allow it.
- Treating an account alias as a security feature. It only makes the sign-in URL friendlier.
- Using root for daily work. Use an IAM user instead.
- Assuming MFA on root also covers my IAM user. MFA belongs to each identity.
