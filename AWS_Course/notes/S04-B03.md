# S04-B03: Access Keys, the CLI and SDK, and CloudShell

Udemy (Stéphane Maarek), Section 4. Exam link: Task 1.2 (application configuration and credentials security) and Task 1.1. Reviewed 2026-11-03.

## 1. The big idea

People and programs need ways to call AWS beyond the console, and every way in needs credentials. This block covers the three ways in, how each is protected, and the option that avoids storing a secret at all.

## 2. Three ways to reach AWS

- **Management Console:** protected by a username, a password, and ideally MFA.
- **CLI (Command Line Interface):** a tool you run in a terminal. Commands start with aws, they call AWS's public APIs, and they can be scripted. It is open source. Protected by access keys.
- **SDK (Software Development Kit):** libraries for one programming language (JavaScript, Python, Java, Go, Node.js, C++, and more, plus mobile and IoT), embedded in application code. Protected by access keys. The CLI itself is built on the Python SDK, called Boto.

## 3. Access keys

- **Two parts:** an access key ID (like a username) and a secret access key (like a password).
- **Where they come from:** created in the console under Security credentials. The secret is shown only once. The key ID stays visible afterward.
- **Handling:** each user manages their own keys. Never share them, and never put them in code, chat, screenshots, or the repo.
- **Setup:** aws configure asks for the key ID, the secret, a default Region, and an output format. A named profile (--profile) keeps the default profile untouched.
- **Lifetime:** keys do not expire on their own. They stay valid until they are deactivated or deleted.
- **Permissions:** a CLI call has exactly the permissions of that user's policies. Remove the policy and the call is denied (access denied, exit code 254).

## 4. Authentication vs. authorization

- **Authentication:** who are you? Passwords and MFA in the console. Access keys for the CLI and SDK.
- **Authorization:** what may you do? The policies attached to the user or its groups.
- **get-caller-identity** works with no permissions. It only answers who am I. A command like list-users needs a policy that allows it.
- A valid key with no policy still gets access denied.

## 5. CloudShell and the alternatives

- **Alternatives:** when you create a key, the console recommends CloudShell, or the CLI v2 with IAM Identity Center. They exist to avoid long-lived keys.
- **CloudShell:** a free terminal in the browser. It runs with your console sign-in, so there is no access key to create, store, or delete.
- **Details:** the CLI is preinstalled, the default Region is the one you are in, files persist between sessions, and you can upload, download, and open several tabs.
- **Limit:** it is not available in every Region.

## 6. Rotating a key safely (what I practiced)

- **Why it works:** IAM allows two keys per user, so you can test the new key while the old one still works.
- **Order:** free a slot by deleting an unused Inactive key. Create the new key. Put it in a temporary named profile and test it. Deactivate (do not delete) the old key. Confirm the old key now fails (InvalidClientTokenId) and the new one works. Swap the profile names. Then delete the old key.
- **Rule:** never delete the old key before the new one is proven. Deactivating is reversible, and deleting is not.
- **Who does it:** an admin IAM user, never root.
- **No CSV:** copy the secret straight into the terminal. Delete any key file you did download.

## 7. Decision rules (requirements lead to choices)

- Occasional admin commands and no stored secret: CloudShell.
- A script or automation outside AWS: the CLI with private, rotated credentials.
- Code inside an application: the SDK. Supplemental: never hard-code keys. For an app running on AWS, a role is better than keys (next block).
- A command worked and is now denied while the key is still Active: a policy or group membership changed (authorization).
- A key is old or may have been exposed: rotate it.

## 8. Mistakes to watch for (from my own misses)

- Describing the alternatives as a way to keep long-term access. They exist to avoid long-lived keys.
- Calling a denied command a "silent deny." It is an access denied error with exit code 254. A pager or terminal view can hide it.
- Treating only authentication as the point. A key authenticates, and a policy authorizes.
- Leaving downloaded key files on the machine. Delete them, or store the secret in a password manager.
- Thinking rotation needs root. An admin IAM user does it.
