# S04-B05: IAM Best Practices and Section Summary

Udemy (Stéphane Maarek), Section 4. Exam link: Task 1.1 (security best practices for IAM and root users). Reviewed 2026-11-11.

## 1. The big idea

IAM mistakes are easy to make and costly. This block turns the whole section into one checklist, so a mistake can be spotted before it happens.

## 2. The checklist

- **Root:** use it only to set the account up, then stop. Give it MFA.
- **One user = one physical person.** Never share a login. Create another user for a friend or teammate.
- **Groups:** put users in groups and attach permissions to the groups, so security is managed at the group level.
- **Password policy:** create a strong one.
- **MFA:** enforce it wherever possible, starting with the most powerful identities.
- **Roles:** use roles whenever an AWS service needs permissions, including EC2 instances.
- **Access keys:** needed for the CLI or SDK. They are as secret as passwords. Never share users or keys.
- **Review permissions:** use the Credentials Report (account level) and Access Advisor (user level).

## 3. The section in one pass

- Users map to real people and can have a console password.
- Groups hold users only.
- Policies are JSON documents that outline permissions for users or groups.
- Roles are identities for services such as EC2.
- MFA and a password policy protect logins.
- The CLI and SDK manage services from a terminal or from code, using access keys.
- The two audit tools show how IAM is being used.

## 4. Why each rule exists

- **Limit what an identity can do:** groups, policies, least privilege.
- **Protect how it proves who it is:** passwords, MFA, secret keys.
- **See and trace what is happening:** one person per user, and the two reports.
- **One user per person:** accountability. If a login is shared, nobody can tell who made a change, and one person's access cannot be removed without cutting off the others. Supplemental: the record of who made which API call is CloudTrail.

## 5. Password policy vs. MFA

- **Password policy:** controls the password itself, such as length, character types, whether users can change their own password, expiration, and preventing reuse.
- **MFA:** a separate control, turned on for each identity.
- **A password policy cannot require MFA.**
- Caution: do not turn on expiration with "requires an administrator reset" while only one console admin exists.
- Allow users to change their own password, or only an administrator can reset it.

## 6. Decision rules (requirements lead to choices)

- Nobody can tell who made a change: one IAM user per person, with permissions in groups.
- A password alone must never be enough to sign in: turn on MFA for each user. A longer password policy does not do this.
- A contractor leaves: remove all of their access, both the console password and any access keys.
- An app on EC2 needs AWS access without a stored key: a role with only the permissions it needs.
- I need to know who lacks MFA or has stale credentials: the Credentials Report.
- A console user never signs in: remove the password rather than protect it.

## 7. Auditing my own account against the checklist

- I predicted which items my account did not meet. I got two right, and the check found a third.
- A report showed that a CLI-only user had a console password that was never used. I removed it.
- I set a custom password policy, and noticed that one setting stopped users from changing their own password.

## 8. Mistakes to watch for (from my own misses)

- Thinking a password policy can require MFA. It cannot.
- Answering the question I expected. The Credentials Report finds who lacks MFA. The fix is turning MFA on.
- Assuming I had a custom password policy when only the default was in place. Check the real setting.
- Leaving an unused console password on a CLI-only user.
- Unticking "users can change their own password" without meaning to.
